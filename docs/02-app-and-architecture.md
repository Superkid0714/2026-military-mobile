# 앱 구현과 로컬 구성

## 기술 구성

| 역할 | 기술 | 적용 내용 |
| --- | --- | --- |
| 앱·화면 | Flutter / Dart | Android 태블릿, 한국어, 반응형 배치 |
| 상태·이동 | Riverpod / go_router | 저장 상태 공유와 화면 이동 |
| 저장 | Drift / SQLite | 내부 테이블, 검색·집계·마이그레이션 |
| 촬영·파일 | Camera / path_provider | 미리보기, 원본과 앱 내부 저장 |
| 화면 자산 | flutter_svg / 번들 폰트 | 외부 다운로드 없는 화면 구성 |
| 학습 | Python / NumPy | PC에서 합성 모델 학습 |
| 추론 | Dart / JSON | 태블릿에서 매개변수 계산 |

검증 개발 환경은 Flutter 3.47.7, Dart 3.13.5입니다. Android 최소 API는 24, 대상 API는 36입니다. 전 기종에 대한 검증을 의미하지 않습니다.

## 화면별 기능

| 화면 | 동작 |
| --- | --- |
| 종합 현황 | 차량 수, 상태 구간, 정비 요약, 우선 조회 차량 |
| 차량 현황·상세 | 검색·필터·정렬, 누적값과 관련 이력 |
| 정비 분석 | 기간·계통·월별 정비 건수와 비용 |
| 정비 기록·상세 | 검색·필터·정렬, 12건 단위 페이지와 상세 |
| 데이터 입력 | 정비·운용 저장, 누적값 감소 검사, 분류 제안 |
| 점검 | 카메라·촬영, 수동 메모, 원본·세션 저장 |
| 분석 이력 | 예측 결과, 모델 버전과 갱신 사유 |
| AI 정비지원 | 차량·차종·표준부품·증상별 문서 원문 검색, 관련 정비·촬영 이력, 질문 저장 |
| 잔여 정비거리 | 확인한 주기·마지막 교환일·교환 계기를 등록하여 거리 계산, 기준 수정·삭제 |
| 연간 정비계획 | 최근 90일 운용 추세를 이용한 다음 1회 정비 예상일, 연도·차량별 조회 |
| 데이터 관리 | 백업·복원, 전체 운용 기록 페이지 조회·수정·삭제, 변경 전후 이력 비교 |

상태 구간은 목업 추정치를 화면에 나눈 것으로 실제 차량 안전 판정 구간이 아닙니다.

## 다중 모듈 정비지원 반영 (2026-10-14)

종합 현황 → 차량 상세 → AI 정비지원 → 현장 점검 → 연간 정비계획을 연결했습니다. `brake_pad`, 브레이크 패드, 제동패드 등은 표준부품명으로 통일합니다. 촬영 시 수동 지정한 부품을 같은 차량의 근거·정비 이력과 연결하고, 정비지원에서 해당 촬영 세션 상세로 돌아갈 수 있습니다.

문서 근거는 차종, 부품, 증상 키워드, 문서명·개정판, 원문 위치와 본문 구간을 직접 등록합니다. 차종을 일치시키고 부품·키워드로 상위 5개 원문 구간을 조회합니다. 초기 구현은 로컬 키워드 검색이었습니다. 현재는 아래의 로컬 임베딩 혼합 검색·선택형 원문 추출 요약도 연결되어 있으며, [실제 PDF 반입 절차](13-local-pdf-workflow.md)를 따릅니다. 교범 원문과 권장 주기는 기본 제공하지 않으며 현장에 맞는 자료를 확인하여 등록해야 합니다.

잔여 정비거리는 `max(0, 주기 - (현재 계기 - 마지막 교환 계기))`로 계산합니다. 새 정비 기록에는 교환 완료 여부와 당시 계기를 저장할 수 있으며, 확인한 교환 완료 기록을 다음 계산의 기준으로 사용합니다. 교환 여부·계기가 없는 과거 기록은 근처 운용 기록으로 추측하지 않습니다. 기준일 당일 또는 이후에 같은 부품의 교환 여부 미확인 기록이 있으면 계산을 보류합니다. 같은 날짜의 작업 순서는 날짜만으로 알 수 없으므로 확인을 요청합니다. 이 계산은 기존 합성 모델의 다음 달 고장수리 확률과 별개입니다.

연간 계획은 최근 90일 중 첫·마지막 운용 기록의 거리 증가량과 관측일 수를 이용합니다. 2건 이상, 관측 간격 7일 이상, 양의 거리 증가, 마지막 기록 30일 이내일 때만 다음 정비일을 추정합니다. 정비 주기가 도달한 항목은 오늘로 표시하고 이후 반복 교환은 가정하지 않습니다. 추정 불가 및 선택 연도 밖의 항목도 전체 주기 목록에서 확인할 수 있습니다.

근거와 주기는 SQLite 메타정보에 보관하고 기존 사진 포함 백업에 함께 저장·복원합니다. 기존 백업도 읽을 수 있습니다. 공개 객체탐지 어댑터와 선택형 추출 요약을 연결했으며, 실제 부품 식별·정비 판단은 사용자가 확인합니다. 기존 가상 차량 및 합성 모델의 차종·성능 범위는 그대로입니다.

### 사용성 검증 후 개선

- 증상 검색에 한국어 조사와 흔한 증상 표현을 반영합니다. 예를 들어 ‘시동이 걸리지 않아요’에서 ‘시동’·‘시동 불량’을 함께 검색합니다. 입력 바로 아래에 결과 건수와 원문 미리보기를 표시하고 원문을 대화상자로 열 수 있습니다. 미연결 기능 상태와 질문 저장의 의미도 입력 영역에 표시합니다.
- 선택한 차량과 부품을 촬영 화면으로 전달합니다. 정비지원의 부품·증상·스크롤 위치는 실행 중인 앱의 차량별 상태에 보관하므로 다른 화면에서 복귀하면 이어서 사용할 수 있습니다. 이 임시 상태는 DB나 백업에 저장하지 않습니다.
- 주기 등록에 숫자 키보드·쉼표 숫자·달력을 지원하고 필수값, 날짜 범위와 현재 계기를 항목별로 검증합니다. 첫 오류 항목으로 이동합니다. 정비계획의 등록 버튼은 양식을 직접 열고, 전체 차량 보기에서는 등록 대상을 먼저 선택합니다.
- 근거·정비 주기 삭제 전 대상을 확인하고, 삭제 후 10초 동안 실행 취소를 제공합니다. DB 변경은 최신 자료에 대한 변경 함수를 순서대로 실행하므로 되돌릴 때 그 사이 추가한 다른 자료를 덮어쓰지 않습니다. 같은 차량·부품의 새 주기가 있으면 복구를 거부하고 안내합니다. DB 스키마 변경은 없습니다.

## 저장 구조

### 실사용 준비와 정비 완료 (v0.2.0)

실사용 준비 화면에서 차량번호·차종·출고연도·누적 거리·시간·유류를 등록하고, 사용 가능한 문서 근거와 확인한 정비 주기를 준비할 수 있습니다. 차량과 초기 운용 계기는 한 트랜잭션으로 저장합니다. 한글 차량번호를 지원하며 예제 전용 번호와 중복 번호를 거부합니다. 등록 차량이 있으면 종합 현황과 기본 차량·정비 목록 및 분석 집계에서 예제를 제외합니다. 차량 목록에서 예제를 함께 조회할 수 있습니다. 등록 차량에는 합성 목업 고장 확률을 적용하지 않습니다.

점검 상세에서 정비 등록을 열면 차량·부품·메모를 이어받고 원본 사진을 확인합니다. 정비 기록에는 점검 ID를 연결하여 같은 차량의 사진만 참조할 수 있습니다. 부품 교환 완료를 선택한 경우 당시 계기를 입력하며, 단순 점검·수리는 교환 기준을 초기화하지 않습니다.

다음 계획의 교환 기준은 저장된 완료 기록에서 계산합니다. 완료 기록 수정·삭제도 즉시 반영되므로 별도 기준 복사본이 남지 않습니다. 교환 완료 화면은 잔여 거리와 저장된 기록·연결 사진·다음 계획으로 이동하는 액션을 제공합니다. 운용 관측이 부족하면 잔여 거리는 표시하고 예상 날짜는 관측 축적 후 제시합니다. 주기가 없으면 확인한 주기를 등록하도록 안내하며, 이때 기존 교환 완료일·계기를 이어받을 수 있습니다.

정비 기록의 점검 ID·교환 여부·교환 계기는 선택 필드로 추가하여 기존 DB와 백업을 계속 읽습니다. 같은 차량 참조와 누적 계기 범위를 검증하고, 사진 포함 백업·복원에도 연결 정보와 완료 결과를 유지합니다.

교환 여부는 미확인(null)·교환 없음(false)·교환 완료(true)를 명시적으로 선택합니다. 새 입력의 기본값은 미확인이며, 수정 중 사용자가 바꾸지 않은 값은 유지합니다. 정비지원·정비계획·종합현황에서 잔여거리 보류의 원인 기록과 ‘확인하기’를 제공하며, 해당 기록 수정 화면으로 연결합니다. 여러 미확인 기록 중 일부만 해소하면 나머지 기록에 따른 보류는 유지합니다.

자료 반입은 기존 MaintenanceEvidence·MaintenanceRule·Maintenance 형식을 재사용합니다. 부품 개념의 명시적 별칭과 품번 후보·원문 적용조건을 분리하고, 출처 미확인 실적은 활성 정비 이력과 분리한 검토 대기로 저장합니다. 등록 차량의 지침 적용조건을 사람이 확인한 뒤 근거 검색과 주기에 연결합니다. 반입은 로컬 파일 선택·미리보기·검증·트랜잭션 순서이며 동일 반입 ID의 재실행은 중복을 만들지 않습니다. 원문 자료를 앱 자산에 내장하지 않습니다.

반입한 주기는 일반·가혹의 거리·개월 기준을 함께 보존하고 부대 설정으로 선택합니다. 거리와 기간은 독립 판정하며, 관측 근거가 충분할 때만 먼저 도래한 기준을 표시합니다. 교환 계기·날짜·적용조건이 없으면 해당 결과를 확인 불가로 둡니다. 반입 주기의 기준시각 조회는 정책 선택 이력과 기록 변경 전 값을 사용합니다. 기존 수동 주기나 확인시각을 복원할 수 없는 기준은 과거 조회를 추정하지 않습니다. 이 기능은 고장 확률 예측이나 임베딩 검색·LLM 생성의 구현을 뜻하지 않습니다.

차량·정비·운용·점검·질문·예측 이력은 SQLite에 보관합니다. 사진은 앱 내부 파일로 저장하고 점검 기록과 연결합니다. 서버 동기화와 여러 기기 간 자동 공유는 없습니다.

앱 삭제·데이터 초기화 시 기록과 사진이 삭제될 수 있습니다. 파일 내보내기·백업·복원과 정비·운용 기록 수정·삭제를 구현했습니다. 자세한 규칙은 [백업·복원 문서](06-local-data-management.md)를 참고합니다.

## 입력에서 화면 갱신까지

1. 입력을 검증하고 누적값 감소를 거부합니다.
2. 내부 DB에 기록을 저장합니다.
3. 해당 차량의 과거 기록에서 14개 특성을 다시 계산합니다.
4. 번들 모델로 추론합니다.
5. 확률·특성·모델 버전·갱신 사유를 저장합니다.
6. 상태 변경을 알리고 화면을 갱신합니다.

사용자 입력으로 자동 재학습하지 않습니다. 모델 매개변수 해시가 바뀌면 예측을 다시 계산하고, 같은 모델·날짜·특성이면 이력을 중복 추가하지 않습니다.

읽기·갱신을 순서대로 처리하며 기록 ID에 128비트 난수를 사용합니다. 같은 시각의 운용 기록은 저장 순서로 최신을 결정합니다. 정보 부족으로 계산할 수 없으면 미분석 상태를 저장해 이전 확률이 다시 나타나지 않게 했습니다.

## 월중 입력과 목업 교체

학습은 월말 관측을 기준으로 하며 월중 입력은 임시 추정으로 표시합니다. 부분월 정확도는 별도 검증 대상입니다.

이전 목업 교체 시 정비·운용 사용자 입력이 없는 차량의 합성 이력만 바꿉니다. 입력이 있는 차량은 전체 이력을 보존해 서로 다른 가상 이력이 섞이지 않게 합니다. 보존된 이전 이력의 성능은 새 시험 점수로 입증되지 않았습니다.

## 업무 중심 화면 재구성 (v0.3.0, 2026-10-28)

기존 저장·예측·촬영·기록·백업 기능과 DB 구조를 유지하면서 메뉴를 ‘시작과 준비 / 현장 작업 / 기록과 계획 / 관리’로 묶었습니다. 기존 화면 주소는 유지합니다.

종합 현황은 등록 차량 수, 주기 도달 항목, 기준 확인이 필요한 항목, 주기가 없는 차량을 구분합니다. 등록 차량이 있으면 기준 확인·잔여 거리 순으로 다음 정비를 먼저 보여주며, 항목을 누르면 해당 차량·부품의 정비지원 화면으로 이동합니다. 예제 데이터 조회 여부를 상단에 표시하고 합성 예측 도표는 접힌 ‘예제 분석 보기’ 영역으로 옮겼습니다. 최근 정비 기록과 단계별 업무 시작 액션도 제공합니다.

실사용 준비 화면에는 차량·근거·주기의 등록 상태와 다음 준비 단계를 표시합니다. 정비지원 화면은 촬영을 주요 액션으로 배치하고, 사진 없이 선택한 차량·부품의 정비 결과를 바로 기록할 수 있습니다. 질문 저장은 별도 액션으로 유지하며, 기록 저장 후 화면 제목을 ‘정비 완료’로 바꿔 다음 계획 확인으로 이어집니다.

## 네트워크 범위

2026-10-29 정리: CameraX가 추가한 녹음·구형 저장소 권한과 병합 과정의 읽기 권한을 앱 매니페스트에서 제거했습니다. 사진 촬영은 음성 없이 앱 내부 파일을 사용하고, 백업은 시스템 문서 선택기를 사용합니다. 최종 debug APK의 권한과 자동 백업 설정을 자동 검사합니다. 실제 카메라·USB 파일 선택 동작은 실기기 확인이 필요합니다.

차량·기록·정비지원·점검·계획·분석 화면에는 현재 조회 대상의 예제·등록·혼합 여부를 표시합니다. 데이터 입력의 최근 내역과 데이터 관리의 전체 백업 대상도 별도로 구분합니다. 정비 분석의 비용 순위는 집계와 같은 활성 차량 목록을 사용하므로 등록 차량이 있으면 예제 차량을 제외합니다.

운영 앱은 로그인, 원격 API, 클라우드 동기화, 모델 다운로드를 사용하지 않습니다. 폰트·이미지·목업·예제 모델을 번들로 포함하고 실제 임베딩 모델과 문서 색인은 별도 로컬 파일로 반입합니다. 개발 PC에서 SDK·패키지·공개 모델을 준비하는 과정에는 네트워크가 필요할 수 있으며 원문은 전송하지 않습니다.

인터넷 권한을 제거한 개발 APK는 네트워크 기반 디버깅에 제한이 있어 재빌드·USB 설치로 확인합니다. 이 설정만으로 별도 보안 인증이나 감사를 완료한 것은 아닙니다.

## 사양 적응형 실행 기반 (2026-10-31)

시연 기기 한 종류에 맞춘 RAM 기준을 두지 않습니다. 앱 시작 시 Android가 보고하는 총·가용 RAM, CPU 가용 코어 수, 지원 ABI, Android API, 앱 내부 저장공간 여유와 저메모리 상태를 읽습니다. 데이터 관리 화면 맨 아래 ‘기기 사양·모델 단계 설정’에서 조회하고 자동 선택보다 낮은 단계 상한을 저장할 수 있습니다. 모델 요청 직전에도 사양을 다시 읽는 진입점을 제공합니다.

`model_execution.dart`는 기본·확장·생성 단계와 실측 근거가 필요한 선택 규칙을 분리합니다. 검토된 실기기 기준은 아직 등록하지 않았으므로 자동 선택은 기본, LLM은 꺼짐입니다. 별도 사용자 요청 한 번에만 선택 LLM 시험을 허용하며 RAM 기준을 임의로 확정하거나 자동 승격하지 않습니다. 실제 임베딩·공개 Vision 어댑터와 선택 LLM을 연결했습니다. 세 번째 모듈은 규칙 기반 잔여 정비거리 + 정비기록 분류이며 미래 고장 예측을 하지 않습니다. 기존 예제 JSON 모델을 이 실행 기반의 실모델로 취급하지 않습니다.

`ModelExecutionManager`는 모델 요청을 직렬화하고 각 요청의 로드·추론·해제를 수행합니다. 실패 시 프로세스 종료를 확인한 뒤 작은 모델 후보로 진행하며, 종료 확인 실패 시 추가 로드를 금지합니다. LLM 후보가 없으면 `retrieval_only`, 다른 모델 후보가 없으면 `unavailable`을 반환합니다. 정비지원의 실제 임베딩·선택 요약과 저장 이미지의 공개 Vision 시험이 이 실행기를 사용합니다. 원문 키워드 검색·잔여거리·기존 연계 조회는 모델 실패 시에도 유지합니다.

Android `ModelWorkerService`는 `:model_worker` 별도 프로세스와 전용 추론 스레드를 사용하며 외부에 공개하지 않습니다. 같은 앱 UID의 프로세스 분리이며 보안 샌드박스 격리나 별도 권한 부여를 뜻하지 않습니다. 최초 기반 검증 후 ONNX CPU 임베딩 어댑터를 추가했습니다. 실제 OOM과 실기기 동작은 여전히 미검증이며 단위 테스트 대역과 실제 ONNX 계측을 구분합니다.

LLM은 측정 규칙의 Android API 조건에 더해 설치 모델에 명시한 `minAndroidApi`를 충족해야 합니다. 요구 수준 미명시 또는 미충족 시 로드하지 않습니다. 사양 감지는 카메라 정책 차단·하드웨어·권한·AppOps를 포함하고 실제 열기 실패도 반영합니다. 개인정보 보호 토글의 현재 상태는 공개 API로 확정하지 않습니다. 카메라 사용 불가 시 Vision을 끄고 수동 부품 선택에서 근거·이력·정비 등록으로 이어집니다.

## 사용자 확인 연결과 실제 임베딩

정비 저장은 이름 일치로 `conceptId`를 자동 확정하지 않습니다. 입력 화면에서 개념을 선택하고 확인해야 `conceptConfirmedAt`과 함께 저장합니다. 확인시각 없는 과거 연결은 미확인 후보입니다. 다른 필드만 수정하면 확인 정보를 유지하고 품명을 바꾸면 해제합니다. 미확인 후보는 이력 화면에 구분해 표시하고, 주기 계산에 영향을 줄 수 있는 후보는 보류 원인과 확인 경로로 연결합니다. 기준시각 이후의 확인을 과거 계산에 쓰지 않습니다.

PC에서 준비한 INT8 인코더에 원 모델의 평균 풀링·Dense/Tanh·정규화를 연결하고 문서 조각 벡터를 생성합니다. `.mrag`는 모델·어휘·색인·등록 근거·라이선스·파일 해시를 담습니다. Android는 파일 선택기로 로컬 복사 후 크기·구성·해시를 검증하고 교체하며, 근거 반입은 기존 `importKnowledge` 검증·트랜잭션을 사용합니다. 모델 파일은 일반 기록 백업에 포함하지 않습니다.

기존 키워드 검색은 즉시 유지합니다. 설치 후 ‘임베딩·키워드 혼합 검색’을 누르면 기존 차량·부품·기준시각과 확인한 적용 문서 조건을 먼저 제한한 뒤 실제 질문 임베딩과 원문 조각 벡터를 비교합니다. 일반·가혹 및 거리·기간 조건을 우선하고 문서별 최대 유사도 순위와 키워드 순위를 RRF로 합쳐 최대 5건을 표시합니다. 원문·모델·색인 불일치나 실행 실패 시 키워드 검색으로 복귀합니다. 검색 관련성 평가와 자유 생성 답변은 별개입니다.

## 선택 LLM과 공개 Vision 어댑터

실기기가 여러 대 없어도 개발을 진행할 수 있도록 RAM 3/4GB·스레드 2/4개의 에뮬레이터 반복 시험을 수행했습니다. 현재 묶음의 운영 가안은 기본 업무 3GB 시작 목표·2스레드·LLM 꺼짐, 선택 LLM은 4GB 권장 시작 등급입니다. 가용 메모리 1.5GiB 여유값은 측정된 작업 프로세스 PSS에 설계 여유를 적용한 가정이며 자동 판정 코드에 넣지 않았습니다. 에뮬레이터만으로 실기기 최소 사양을 인증하지 않으며 기존 `MeasuredTierRule`의 실기기 근거 요구는 유지합니다. 자세한 수치와 한계는 [검증 문서](05-validation-and-next-steps.md)를 따릅니다.

LLM은 고정 리비전의 llama.cpp를 Android API 28·64비트 CPU용 JNI로 빌드하며 앱 전체 minSdk 24를 유지합니다. API·프로세스 ABI·설치 파일·사용자 하향 상한·저메모리 상태를 확인합니다. 자동 판정은 기본 단계에 머물고 정비지원의 명시 요청 한 번만 생성 단계를 엽니다. 같은 `:model_worker` 슬롯에서 임베딩을 해제한 뒤 Qwen3-0.6B Q4_0을 로드하며, 모델·컨텍스트·샘플러를 닫습니다. 생성의 120초 제한은 임시 인프라 watchdog이고 사용자 응답시간 기준이 아닙니다.

검색 근거 두 개에서 숫자 없는 완전한 문장 후보를 추출하고 질문과 함께 입력합니다. 줄바꿈·공백만 파생 입력에서 정규화하고 원문·색인·해시는 변경하지 않습니다. 모델 출력은 후보 문장 하나 또는 무응답으로 문법 제한하며 64~128 출력 토큰 상한을 받습니다. JSON 형식·출처 ID·문장 전체 일치·수치 제외를 독립 검증하고 불일치·무응답·잘림·실행 실패면 원문을 표시합니다. 인용 버튼에서 해당 근거 위치와 원문을 확인합니다. 이는 일반적인 의미 함의 자동 검증이나 질문 관련성 보장이 아니라 출처를 확인하는 추출 요약입니다. 교환주기 수치는 기존 등록 규칙·부대 선택만 사용합니다.

Vision은 공개 SSD MobileNet INT8을 같은 ONNX CPU 슬롯에서 실행합니다. 앱 내부 저장 이미지에 대해 크기 확인·EXIF 방향 처리·300×300 RGB UINT8 변환 후 추론하고 세션을 닫습니다. 모델 점수 0.5는 실행 시험용 표시 기준이며 검증된 부품 탐지 임계값이 아닙니다. COCO에 대한 검토된 부품 대응표는 비어 있으므로 일반 사물을 부품으로 억지로 매핑하지 않습니다. 대응 후보는 별도 인터페이스로 제공하며 자동 확정하지 않습니다.

점검 기록에는 선택적 탐지 메타데이터와 부품 개념 확인시각을 저장합니다. 입력 DTO의 확인값은 신뢰하지 않고 명시 확인 인자로만 확정합니다. 원본 사진이나 부위를 바꾸면 확인을 해제하고 사진 변경 시 분석 결과도 해제합니다. 메모 수정은 확인을 유지하며 백업에서 선택 필드를 보존합니다. 촬영 세션 ID를 부품 근거 화면에서 정비 입력까지 전달하고, 정비 기록의 개념 연결은 별도 확인을 받습니다. 카메라가 차단되면 생산 경로의 Vision 실행을 끄고 수동 선택을 유지합니다. 공개 파일을 이용한 어댑터 계측은 카메라 하드웨어 시험과 구분합니다.

선택 요약의 질문 상한은 유니코드 문자 120개입니다. 넘으면 앞부분을 잘라 답하지 않고 `retrieval_only`로 전환합니다. 각 근거의 앞 1,800문자에서 숫자 없는 완전한 문장을 최대 두 개씩 후보로 만들며, 후보가 없으면 원문을 유지합니다. 네이티브 컨텍스트 1,536토큰·배치 128·마이크로배치 64·출력 상한 64~128은 이번 실행 설정이며 검증된 최소 기기 사양이나 검색 품질 기준이 아닙니다.

## 규칙 기반 잔여 정비거리 + 정비기록 분류

이 명칭이 세 번째 모듈의 공식 이름입니다. 등록한 주기·기준 계기·교환 상태로 잔여 정비거리와 기간을 판정하고, 문장 분류는 계통 후보만 제안합니다. 현재 동작을 ‘예측정비’로 부르지 않습니다. 검증된 시계열 정비이력이 확보되면 기존 규칙·근거·차량·기준시각 연결을 유지하면서 예측 모델을 별도 어댑터로 확장할 수 있습니다. 합성 고장 확률과 과거 개발 기록은 예제·과거 기록으로 구분합니다.

`tools/train_system_pilot.py`는 로컬 정비 내용만 입력으로 사용하고 별도 품명·차량·날짜·금액·출처·라벨 문구는 특성에서 제외합니다. 알려진 차량 식별 문자열과 숫자를 제거한 뒤 문자 2~4그램을 FNV-1a32로 4,096차원 이진 해시 특성으로 변환합니다. 다항 나이브베이즈를 MatMul/Add/Softmax ONNX로 내보냅니다. 147,717바이트 FP32 모델로 별도 양자화는 하지 않았습니다.

`.msystem` 반입은 구성·파일 크기·해시·필수 출처 상태를 검사하고 임시 디렉터리 검증 후 교체합니다. 같은 `:model_worker` 슬롯의 ONNX CPU 어댑터로 실행·해제하며 API 24 기본 단계입니다. 질문 임베딩이나 Vision·LLM과 동시에 모델 세션을 유지하지 않습니다. 원문 정비 문장은 작업 프로세스로 전달하지 않고 해시 특성만 전달합니다.

등록 차량의 정비 입력 화면은 설치된 파일럿의 ‘계통 제안 받기’를 제공합니다. ‘단일 AI 라벨 초안·사람 독립 검토 없음·원자료 작성 경위 미확인’을 표시하며 점수를 검증된 확률로 부르지 않습니다. ‘이 계통 선택’을 눌러야 필드가 바뀌고, 원문을 수정한 뒤에는 이전 제안을 숨깁니다. 실제 부품 개념 확정과 교환 여부는 별도 확인입니다. 합성 문장 모델 제안은 예제 차량에만 표시합니다. 차량 단위 미래 고장 확률 모델로 전환한 것이 아닙니다.
